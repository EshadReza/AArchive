# S004 - Development services and CI

Completed: 2026-10-06. Prerequisites: [S002](S002.md), [S003](S003.md).
Requirements: SRS Sections 17, 55 and 56; decision D01.

## Delivered

- `compose.yaml` with digest-pinned PostgreSQL 17.11 and Redis 8.2.10 images,
  readiness checks, loopback-only published ports and project-scoped named volumes.
  PostgreSQL reads credentials from ignored local configuration; Redis persists
  through AOF. Application processes run on the host. No cloud services or worker
  application were introduced.
- Vite proxies `/api` to Django at `127.0.0.1:8000`, with server-only
  `AARCHIVE_API_TARGET` available for another local backend port. Host, Origin and
  cookies are preserved; no CORS exception or disabled CSRF check is needed.
- `.github/workflows/ci.yaml` runs backend and frontend jobs on push, pull request
  and manual dispatch. Actions use verified release commit SHAs, workflow
  permissions are read-only, and CI uses disposable synthetic database credentials.
- `scripts/check_backend.sh` shares the actual locked backend gate with CI,
  forces test settings, and requires an explicit `TEST_DATABASE_URL`. The backend
  suite now includes a real PostgreSQL transaction rollback test.
- `npm run check` shares frontend lint/type/unit/build checks with CI. CI also
  runs the five Chromium checks and validates Compose configuration.
- `scripts/check_dev_proxy.py` starts isolated ephemeral Django/Vite servers and
  verifies proxied health, Host/cookie preservation, valid CSRF, missing-token
  rejection and foreign-origin rejection. Its test-only URLconf is not part of
  normal application routes. Cleanup stops only its own process groups.
- README start/stop/reset instructions, connected VS Code terminal commands,
  health smoke URL, CI notes, and matching API/database/security guides.

There are no account/domain migrations, new business APIs or new website feature
screens. Redis is available as infrastructure; application job/cache use comes
in later sprints. No user `.env` or existing development data was overwritten.

### Failure detection

Created a temporary source copy under `/tmp/aarchive-s004-negative-mkjdjjnh` and
added one deliberately failing test there. The repository was not modified by
the probe. The exact `bash scripts/check_backend.sh` gate exited **1**: the 38
real tests passed and the intentional `pytest.fail(...)` test failed. An initial
`assert False` probe was also rejected earlier by Ruff. Both checks demonstrate
that failures stop the shared gate rather than being suppressed.

### Persistence and cleanup

Wrote a synthetic PostgreSQL row and Redis key into the isolated project's stores.
Ran `down` without volume deletion, then `up -d --wait`. Both services returned
healthy; PostgreSQL returned the original value `4`, and Redis returned
`verified`. Redis reported version 8.2.10. This confirms named-volume persistence
through container recreation.

Finally ran `docker compose --env-file .env.example -p
aarchive-s004-verify-1006 down --volumes`. Only the verification project's
containers, network and test-data volumes were removed. Application smoke/browser
servers stopped at the end of their checks. Downloaded images can remain cached.

## CI scope and handoff

The workflow's actual install/check commands were executed locally and its action
inputs were checked against the pinned official action metadata. A GitHub-hosted
run has **not** been performed; it will run after the workflow is pushed. No remote
push or deployment was requested or performed.

The implementation follows [Compose readiness guidance](https://docs.docker.com/compose/how-tos/startup-order),
[Vite proxy configuration](https://vite.dev/config/server-options), and
[GitHub service-container guidance](https://docs.github.com/en/actions/tutorials/use-containerized-services).
After S004 was marked DONE, `python3 scripts/sprint_context.py --check` passed and
`--next --brief` selected **S005 — platform users and account states**. G01 exporter schemas remain
an input for S025; they do not block this foundation work.
