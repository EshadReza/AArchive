# S005 - Platform users and account states

Completed: 2026-10-06. Prerequisite: [S002](S002.md).
Requirements: SRS Sections 9, 16.1, 19 and 44; AUTH-002/AUTH-003; decision D02.

## Delivered

- `backend/apps/accounts/`: custom `User` based on Django `AbstractBaseUser`,
  `UserProfile`, `UserRole`, fixed role/state enums and a minimal account manager.
  `AUTH_USER_MODEL=accounts.User` is configured before `0001_initial`.
- UUID identity, canonical unique institutional email, optional unique student ID
  with multiple SQL NULLs allowed, minimal display-name profile, lifecycle and
  verification/approval fields. Database CHECKs reject unknown roles/states,
  noncanonical identifiers and eligible states missing activation prerequisites.
- `create_user(email, password=None, *, display_name="", student_id=None)` creates
  a pending Student and profile in one transaction. No password means an unusable
  credential. Raw passwords use Django hashing; known Django encoded hashes are
  rejected. Privilege/source fields are not accepted as creation arguments.
- Eligibility predicates for login, current sessions and historical access, plus
  `eligible_for_authentication()` for a fresh database query. ACTIVE, INACTIVE,
  GRADUATED and ALUMNI require verification/any required approval; PENDING,
  SUSPENDED, ARCHIVED and ANONYMIZED deny eligibility. Correct passwords alone
  cannot activate an account. History eligibility remains subject to permissions.
- Protected profile/role references and stable identity through state changes.
  Academic models do not exist yet; their future FKs must preserve this identity.
- The shared backend/CI gate now checks migration drift. Documentation describes
  the actual schema, creation boundary, predicates, current feature limits and
  developer migration commands.

Full storage choices and field limits are in [database.md](../database.md#implemented-account-foundation-s005).
Email is lowercase in full; student IDs are uppercase strings, preserving leading
zeroes, with blanks normalized to NULL. No institution-specific ID format or
domain allow-list is guessed. Imported identities remain separate future models.

## Migration and next-sprint boundaries

Developers must run the README migration command before using account models.
Initial rollback drops the account tables: the demonstrated reversal is for empty
disposable databases only. Once users exist, use forward corrective migrations
and tested backups. Initial migration and source must be committed together.

Role mutation/bootstrap and scoped grants belong to S007; no alternate Django
Group, `is_superuser`, `is_staff`, or `createsuperuser` path is enabled. Django
auth/contenttypes/session/admin apps are still absent. S008 must add actual
session authentication, requery current account state and preserve CSRF controls.
S009 owns registration/domain/password-policy checks; S010 owns audited guarded
transitions, terminality and revocation; S084 owns actual anonymization. A state
label alone does not erase data. Direct ORM writes are trusted implementation
tools, not a public or importer mutation API. Import provisioning must supply
explicit validated identity fields and never source credentials/privileges.

Framework references: Django documents creating the custom user in its app's
first migration and the use of `AbstractBaseUser` independently of the auth app
in [customizing authentication](https://docs.djangoproject.com/en/5.2/topics/auth/customizing/).
Database checks and uniqueness use Django's [constraint API](https://docs.djangoproject.com/en/5.2/ref/models/constraints/).
