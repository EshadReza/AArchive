# S013 — Reusable course catalog

Completed 2026-10-11 for ADMIN-010, SRS 13/16.2/44/47 and D03, after verifying
S012's models, archive rules, API primitives and shared transaction boundary.

## Delivered

- Department-owned UUID Course with canonical code, title, exact decimal credits,
  description, archive state and revision. No Batch/Term/Section FK or duplicated
  per-term catalog. Same codes in different departments are allowed; duplicates
  within one department fail, including archived codes.
- Protected Department FK and PostgreSQL trigger rejecting reassignment. Explicit
  admin create/edit/archive services reauthorize under the privilege lock and
  commit with reviewed before/after audit; description text is represented by a
  digest in immutable audit records.
- Paginated catalog API with search/department/archive filters, strict payloads,
  current-role filtering and revision conflicts. Admins see all records; Teachers
  read only available courses in active departments. Ordinary/anonymous users and
  stale/closed accounts cannot enumerate the management catalog or mutate it.
- `/admin/courses` management UI with named department selection, forms, filters,
  safe plain-text descriptions, decimal-string credits and focused archive review.
  Existing parent-picker and UI primitives are reused. `/account` links to it.
- Archive retains all catalog data while blocking edits and new offerings. The
  future offering-context helper validates course/department and S012 structure
  within the caller's transaction. Tests validate one Course UUID against multiple
  Terms without creating offerings; real offering persistence remains S014.

The [course catalog guide](../course-catalog.md) covers exact API requests,
projections, permission rules, credit bounds, archive policy and future integration.
README, architecture, API/database/security, audit/access, structure and D03 notes
are updated. No batch offering, enrollment, grading, deployment or remote push was
included in this sprint.

## Migration evidence

With test settings, `PYTHONPATH=backend` and the same synthetic database, a Django
script applied migrations, checked the Course table and rejected a direct Department
reassignment inside a rolled-back synthetic transaction, then ran:

```python
call_command('migrate', 'academics', '0002', interactive=False, verbosity=0)
call_command('migrate', interactive=False, verbosity=0)
call_command('migrate', interactive=False, verbosity=0)
```

Introspection proved reversal removed only `academics_course` and its trigger
function while preserving all existing tables. Reapplication restored the Course
table and department-protection trigger; repeated apply was a no-op. This test used
an empty disposable database. Reversal deletes catalog records and is not a repair
procedure for real academic history.
