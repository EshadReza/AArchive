# S010 — Password recovery and lifecycle transitions

Completed 2026-10-09 for AUTH-003, SRS 16.1/18/34 and D02, after inspecting
S008-S009 code/evidence and resuming the interrupted final verification.

## Delivered

- Generic reset requests, expiring one-use reset confirmation and authenticated
  password changes requiring the current password. New passwords pass the shared
  policy, differ from the old password and are always framework-hashed.
- Digested reset challenges bound to current email/password revision, with atomic
  consumption and invalidation on password changes or lifecycle restrictions.
  Pending, unverified/unapproved, closed and invitation-only accounts cannot use
  recovery to gain access. Alumni/graduates retain recovery and historical eligibility.
- Shared PostgreSQL recovery limits with fixed-window expiry, safe threshold/failure
  audit events and no account enumeration through reset response status/body.
- Administrator-only lifecycle command API, current-state authorization, expected
  state conflicts, recorded prior state for restoration and last-Administrator
  protection. Approval preserves the separate email-verification requirement.
- Proactive deletion of all active subject sessions on password changes and
  suspension/archive. It covers sessions created before this sprint; restoring an
  account cannot revive them. Session deletion, mutation and audit commit together.
- Forgot/reset/change-password screens, generic errors, password clearing,
  explicit submission, URL-fragment removal and no browser credential storage.
- Migration `accounts.0004_passwordreset_user_state_before_restriction_and_more`,
  reset/mail settings, audit catalogue additions and real browser/CI coverage.

The [recovery/lifecycle guide](../recovery-lifecycle.md) documents API payloads,
configuration, state-transition table, local setup, session behavior and limitations.
README, architecture and the API/database/security/access/audit/account decision
guides are updated. No anonymization or full admin account-management UI was added;
those remain S084 and S011 respectively.

## Handoff and limits

Password recovery is enabled locally and explicitly opt-in for production with
validated HTTPS origin/SMTP configuration. Mail is synchronous after commit with
a bounded timeout; requesting another link recovers delivery failures. No durable
mail queue is claimed. Administrative account editing/invitation UI is S011.

Revocation scans active Django session payloads in bounded batches; its work is
linear in active sessions and is not a high-volume performance claim. Legacy
closed accounts without recorded prior state cannot be restored by guessing a
state. New lifecycle commands preserve the prior state and retained identity/history.
Future services must keep the same privilege-lock order and authorization checks.
