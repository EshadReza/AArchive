# S009 — Institutional registration and email verification

Completed 2026-10-09 against AUTH-002, SRS 16.1/18/30 and D02. S008's actual
session API/UI, policy integration and verification evidence were inspected first.

## Changes

- Registration creates only a pending Student with a framework-hashed password,
  exact institutional domain allowlisting and password validation. Existing
  accounts cannot be modified through registration payloads.
- Optional approval is captured per account. Verification alone cannot activate
  an unapproved account, restore a forbidden state, or create an authenticated
  session. Registration/resend responses do not reveal account existence.
- Random verification tokens expire and can be consumed once; only digests are
  stored. Resend replaces the previous token. A keyed account digest invalidates
  links when the account email/password changes. Concurrent verification and
  duplicate registration use the existing privilege lock and transactional audit.
- Shared PostgreSQL budgets cover registration/resend by email and peer; verify
  uses the same peer budget. Expiry permits retry, spoofed forwarded headers do
  not bypass limits, and blocked peers cannot allocate unbounded identifier rows.
- `/register`, `/verify-email` and `/resend-verification` use the existing CSRF
  client, accessible error/status focus and no browser credential storage.
  Verification requires an explicit button click. A browser-discovered bug with
  replacement links opened in the same page was fixed and covered by the real flow.
- Mail adapters are console in development, captured in tests and configured SMTP
  in production. Mail runs after commit; failed delivery gives a safe warning and
  permits resend. Links use a configured origin and a fragment token.
- Added `accounts.0003_emailverification`, reviewed audit events, environment
  validation, frontend/backend tests, and registration coverage in the existing
  isolated browser runner used by CI.

See [registration contract and local setup](../registration.md). Updated README,
architecture, API/database/security/authentication/audit and decision summaries.
No institutional domain was guessed or enabled in a developer's private `.env`.
No real email, remote push or production deployment was performed.

## Operational boundary and next handoff

The empty domain allowlist disables signup until configured. Approval-required
accounts await the later admin lifecycle service. S010 owns password recovery,
audited lifecycle transitions and proactive all-session revocation. It must use
the established privilege lock and cannot bypass verification/approval gates.

Mail delivery is synchronous after commit with a bounded timeout; there is no
durable queue or automatic retry in S009. Resend is the recovery path for delivery
or process failure. Production SMTP credentials/origin, maintenance scheduling and
proxy trust remain deployment configuration. Private runtime artifacts stay out
of Git; migration/source/docs remain committable.
